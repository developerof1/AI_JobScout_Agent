Neither pipeline has a canonical-criteria layer — a named location or department id that gets translated outward into each source's own query shape, and validated inward against each source's own returned text. Healthcare IT's 2 locations × 5 departments, read differently by Built In Chicago and digital-health-jobs.com, need exactly that layer built new.

What this means for the Healthcare IT tab

Against Figure 1 and Figure 2 — what already exists to stand on, and what doesn't.

Reuse as-is

  • Server-rendered HTML + page=N pagination engine contracting_methods/html_pages.py — both candidate sites fit this shape
  • Method-registry dispatch, zero orchestrator changes to add a source METHOD_REGISTRY pattern from contracting_scraper.py
  • Tab + per-tab localStorage state pattern Contracting's hide/unhide, not Scouting's apply-tracking
  • Cron → commit → copy → deploy shape new workflow .yml, same 5 steps as the existing two
  • Token-list substring matching as the validation technique the idea behind JobFilter's location tokens, not the class itself

New — doesn't exist yet

  • Canonical criteria config 2 locations × 5 departments, shared across sources
  • Per-source outbound map canonical id → query param / URL template — no source does this today, all hardcode their query
  • Department as an inbound filter dimension JobFilter only knows location, title, date — department is new
  • New config file, orchestrator script, output JSON, dashboard section config/healthcare_it_sources.json, scrapers/healthcare_it_scraper.py, data/healthcare_it_jobs.json

Migration plan — Figure 1 to Figure 2

Refactor only — Contracting and (paused) Scouting move onto the shared architecture. Healthcare IT is not part of this pass.

  1. Filter Engine

    Generalize JobFilter from hardcoded location/title/date methods to named, pluggable dimensions, each with a per-source support state (composable / fixed / unsupported — plumbing only, nothing exercises "unsupported" yet). Fold in title_matches_keywords() as the title dimension matcher, and deduplicator.py's hash-dedup as a selectable strategy alongside URL-dedup.

    utils/filter_engine.py (new) ← utils/job_filter.py, utils/deduplicator.py, contracting_methods/common.py

  2. Source Registry

    Add a registry that includes the existing html/matador_api methods unchanged, plus two thin wrappers exposing Remotive and Adzuna the same way. No folder rename required — lowest-risk version just adds a new module that imports the old one.

    scrapers/source_registry.py (new) ← contracting_methods/, remotive_scraper.py, adzuna_scraper.py

  3. Tab Config

    Translate search_config.json and contracting_firms.json into the unified shape: sources, dimensions + support state, scoring.enabled, display shape. Keep the old config files in place until step 4 is verified.

    config/tabs/contracting.json, config/tabs/scouting.json (new)

  4. Driver

    One entrypoint, --tab-parameterized, calling Source Registry → Filter Engine → Scoring Engine (if enabled) and writing the output envelope. Highest-risk step — run side-by-side and diff output against current jobs_scored.json / contracting_jobs.json before cutover.

    run_tab.py (new) ← scraper_orchestrator.py, contracting_scraper.py

  5. Output rename

    contracting_jobs.json already fits the {tab}_jobs.json pattern. Rename Scouting's jobs_scored.json → scouting_jobs.json so the dashboard can fetch by one formula. jobs_raw.json/jobs_unique.json were only ever debug intermediates — safe to stop persisting them.

    data/scouting_jobs.json ← data/jobs_scored.json

  6. GitHub Actions

    One reusable workflow_call template runs the shared steps; each tab's workflow becomes a thin caller passing its cron schedule and tab name. Scouting's cron block is commented out here — workflow_dispatch stays, so it's paused, not deleted.

    .github/workflows/_tab_scout_template.yml (new), daily_job_scout.yml, contracting_scout.yml (thinned)

  7. Dashboard renderer + tracking

    One renderTab(tabKey, data) driven by each tab's display shape, and one getTrackedIds(tab, action)/saveTrackedIds(...) pair. Confirmed vs. unclassified job cards render at full vs. reduced opacity here.

    dashboard/app.js ← renderJobs/buildCard, renderContractingSection, getAppliedIds, getHiddenContractingJobs

  8. Cleanup

    Only once step 4's output is verified equivalent: delete the superseded scripts and configs.

    scraper_orchestrator.py, contracting_scraper.py, job_filter.py, deduplicator.py, search_config.json, contracting_firms.json

Order: 1 → 2 → 3 → 4 (verified side-by-side) → 5 → 6 (pause happens here) → 7 → 8. Each step independently revertable; nothing touches the live scheduled workflows before step 6.
Must preserve exactly: the localStorage key strings "appliedJobs" and "hiddenContractingJobs", even inside the generalized tracking helper — a derived/renamed key silently unhides every job a user already hid, the same regression class the contracting hash design already had to guard against once.
